# Démonstration du chantier 2 — faisabilité de la génération (banc E0)

## Ce qui a été construit

- **Banc E0** dans `bench/` (hors build courant, sorties ignorées par
  git) : descriptions de lexeurs **Java, XML, JSON** en JFlex
  (commentaires en français), pilote commun, corpus de ~2 000 lignes
  par langage (déterministes), fichiers de référence et **sorties
  figées relues à la main**.
- **Mesures E0** (§4.4 du plan) : génération (temps, mémoire), vitesse
  de tokenisation (JVM froide et rechauffée), **poids DEX par langage**
  (d8, min-api 26), test de redémarrage, exactitude — tout vert.
- **Profil du dépôt de référence** : la chaîne de chargement des
  grammaires localisée fichier et ligne à l'appui, et mesurée avec ses
  propres bibliothèques (analyse JSON + compilation des motifs) —
  l'hypothèse « le retard vient des grammaires » est **confirmée**.
- Documents : `etude-faisabilite-lexeurs.md` (résultats, licences,
  décisions), `conception-coloration.md` (conception du moteur, **à
  valider avant le chantier 3**).

## Ce qu'on voit (comment rejouer)

Rien à installer : le banc se lance sur la machine de build :

```
sh bench/scripts/run-e0.sh .            # génération, vérifications, mesures, DEX
sh bench/scripts/run-profil-reference.sh <racine-du-clone-du-dépôt-de-référence>
```

Le rapport complet va dans `bench/out/rapport-e0.txt`. La vérification
à la main la plus parlante : ouvrir `bench/data/*-golden.txt` — chaque
ligne est un jeton (type, texte) de la sortie figée — puis retoucher
une règle dans `bench/lexers/java.flex`, relancer le banc : le test
d'exactitude échoue jusqu'à ce que la sortie figée soit relue et
revalidée. C'est le contrat du futur moteur.

## Résultats constatés (machine de build, JVM x86, JDK 17)

| Mesure | Résultat |
| --- | --- |
| Génération | 0,26–0,46 s, 64–73 Mo par lexeur (JFlex 1.9.1) |
| Tokenisation 2 000 lignes, JVM froide | 16,1 / 10,5 / 3,1 ms (Java / XML / JSON) |
| Tokenisation rechauffée | 1,7–3,5 ms, 14–47 Mo/s |
| Poids DEX | 18 788 / 7 804 / 7 420 octets ; **27 612** les trois |
| Redémarrage | vert (202–205 points de contrôle par langage) |
| Exactitude | sorties figées relues, couverture 0 erreur |
| `./gradlew check` | **vert** (le banc n'entre pas dans le build courant) |
| Contrôles de politique | verts (18 fichiers Java, références interdites 62 fichiers) |

Profil du dépôt de référence : 27 grammaires intégrées (1,33 Mo,
4 435 motifs) = **~1,0–1,2 s** de chargement à JIT froide sur JVM x86
rapide (parse 64 ms + compilation 938–1 144 ms) ; la grammaire C++
seule paie 261 ms. Sur téléphone milieu de gamme : plusieurs secondes —
la voie des lexeurs compilés supprime ce coût par construction.

## Décisions soumises au propriétaire

1. **Générateur** : JFlex existant (BSD, outil de build, code généré
   autonome) — *recommandé* — ou générateur écrit par nous.
2. **Code généré committé** : oui (build téléphone léger, exclus des
   contrôles de langue, contrôle d'à-jour) — *recommandé* — ou généré
   à chaque build.
3. **Langages de départ** : Java, Kotlin, XML, JSON + famille
   générique — *recommandé*.
4. **Reprise des descriptions IntelliJ** : par défaut réécrire, reprise
   fichier par fichier possible (Apache 2.0) avec attribution —
   *recommandé*.

Détail, licences et contexte dans `docs/etude-faisabilite-lexeurs.md`.
