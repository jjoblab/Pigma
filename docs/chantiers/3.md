# Démonstration du chantier 3 — moteur de coloration (`:syntax`)

## Ce qui a été construit

- **Module `:syntax` (JVM pur, testé sur JVM)** : contrat du lexeur
  (`Lexer` : fenêtre, état de fin reporté, types sans couleur),
  adaptateur JFlex, **descripteur de langage** (`LanguageSyntax` :
  extensions, lexeur, table type → portée, états redémarrables),
  **portées internées** (`Scope`) et **thème à repli par parent**
  (`SyntaxTheme`), **document ligne par ligne** (`SyntaxDocument` :
  règle d'arrêt, révision par ligne, queue épargnée, écoute du
  tampon, mesures de diagnostic) et **famille générique**
  (`LexerProfile` + `GenericLexer`, SQL livré en démonstration).
- **Lexeurs générés Java, XML, JSON** : descriptions en français dans
  `syntax/src/main/lexers/`, **code généré versionné** (décision 005),
  les constructions multi-lignes (commentaire de bloc, CDATA, balise
  ouverte) traversent les lignes par report d'état ; le JSON distingue
  les clés des chaînes par contexte arrière.
- **Le contrôle d'à-jour** `scripts/check-lexers-fresh` (branché à
  `./gradlew check`, tâche `checkLexersFresh`) : une description
  retouchée sans régénération échoue le build ; sans JFlex il
  s'ignore en le disant (build téléphone vert).
- **Sample** : l'éditeur colore jeton par jeton (une couleur par
  portée, résolue au dessin), quatre langages au sélecteur (Java, XML,
  JSON générés ; SQL générique), deux thèmes **à chaud sans
  retokenisation**, et le **panneau de diagnostic** (première
  coloration, coût de la dernière frappe, lignes relues, jetons) —
  les mesures partent dans `docs/perf.md`.

## Ce qu'on voit (comment rejouer)

    ./gradlew :sample:assembleDebug
    adb install sample/build/outputs/apk/debug/sample-debug.apk

Sur l'écran : le texte Java coloré (mots-clés, javadoc, chaînes,
nombres) ; **XML** → balises, attributs, commentaire multi-lignes,
CDATA ; **JSON** → clés en bleu, chaînes, nombres ; **SQL** →
mots-clés insensibles à la casse, `--`, `/* … */` multi-lignes,
chaîne à apostrophes. Basculer **Clair/Sombre** : les couleurs
changent instantanément, la mesure de première coloration ne bouge
pas (aucune retokenisation). Taper : le panneau « dernière frappe »
reste sous la milliseconde et « lignes relues » vaut 1 ; supprimer un
`*/` : la propagation relit jusqu'à la fermeture suivante.

Côté tests : `./gradlew :syntax:test` — 23 tests, dont les **sorties
figées** (`syntax/src/test/resources/data/*-golden.txt`, relues à la
main : jeton par jeton, états par ligne) et le **test de
redémarrage** (relexer depuis 2 à 205 débuts de ligne en état initial
rend le flux exact — 1 320 lignes de doré au total).

## Résultats constatés

| Mesure | Résultat |
| --- | --- |
| Tests `:syntax` | **23 verts** (dorés, redémarrage, règle d'arrêt, thème, générique, pureté ArchUnit, mesures) |
| Moteur, corpus 2 010 lignes (JVM) | premier lexage **11,8 ms** (26 480 jetons) ; frappe ordinaire **0,03 ms** (1 ligne relue) |
| `./gradlew check` | **vert** (politique 40 fichiers, style, références interdites, à-jour des lexeurs) |
| APK de démonstration | 67 Ko (moteur + 3 lexeurs générés + famille générique) |
| Contrôle d'à-jour | détecte une divergence (vérifié en l'inoculant), s'ignore sans JFlex |

## Limites assumées (et suite)

- La **tokenisation paresseuse par fenêtre** (ne lexe que le préfixe
  demandé) et les **points de contrôle d'état** viennent à l'étape
  E3 : aujourd'hui, le premier appel lexte tout — 12 ms pour 2 000
  lignes sur JVM, à confirmer sur appareil via le panneau.
- Approximations documentées dans les descriptions : valeur
  d'attribut XML non fermée dans la ligne, chaîne Java non fermée
  (erreur sur l'ouvrant) ; la famille générique ignore
  l'échappement par doublement SQL (`''`).
- Kotlin (gabarits de chaîne, pile à internée) : prochain langage de
  la voie générée, après la fenêtre paresseuse.

Prochain chantier : E3 — tokenisation paresseuse par fenêtre, points
de contrôle toutes les ~256 lignes, budget de temps sur le fil
d'interface, puis les plafonds (20 000 colonnes, gros fichier) codés
et mesurés.
