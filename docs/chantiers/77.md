# Chantier 77 — la vue parle au service d'accessibilité (D5)

## La consigne

Le défaut D5 du rapport : la vue ne publiait RIEN aux services
d'accessibilité — ni texte, ni actions, ni événements. TalkBack y
disait « étiquette non définie » et se taisait sur un éditeur de
code entier. Le plan demandait le package `accessibility/`.

## Le correctif

**`editor/.../accessibility/EditorAccessibility.java`** (neuf) :

- **`fillNode`** : la classe `android.widget.EditText`, la vue
  éditable, le texte BORNÉ (fenêtre de 400 caractères autour du
  curseur, ellipse aux deux bouts — le service parle une phrase,
  pas un document de 50 000 lignes), la sélection, huit actions du
  protocole (clic, sélection, coupure, copie, collage, pose de
  texte, mouvements de granularité) ;
- **`fillTextChanged`** : l'événement de frappe (le compte ajouté,
  l'indice, la fenêtre de texte) ;
- **`fillSelectionChanged`** : l'événement de sélection déplacée.

La vue se branche : `onInitializeAccessibilityNodeInfo` remplit le
nœud, `dispatchPopulateAccessibilityEvent` route les événements de
texte et de sélection vers leurs remplissages. Tout passe par
l'API publique de la vue — le package ne touche aucun membre
privé.

Les stubs du vieux harnais suivent : `AccessibilityNodeInfo` (les
actions en constantes, les accesseurs), `AccessibilityEvent` (les
deux types, les indices, les textes), et les trois hameçons du
`View` factice.

## La preuve

Le scénario « accessibilité : le nœud et ses actions » du harnais
réel (Robolectric — les VRAIES classes d'accessibilité) : le nœud
porte sa classe d'éditeur, sa fenêtre de texte bornée (plus courte
que le document), sa sélection, l'action `ACTION_SET_TEXT` ;
l'événement de frappe se remplit. 14 scénarios réels verts, 49/49
au vieux harnais, check complet vert.
