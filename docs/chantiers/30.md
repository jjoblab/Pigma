# Démonstration du chantier 30 — la synchronisation LSP par delta

## Pourquoi ce chantier

La synchronisation intégrale datait du chantier 26 : chaque édition
(amortie de 300 ms) expédiait le texte ENTIERS au serveur — sur le
fichier hors normes, 1,35 million de caractères à travers gson et le
JSON-RPC pour une frappe. Le protocole connaît mieux : la plage
remplacée. La difficulté n'est pas le protocole, elle est les
coordonnées — la plage d'un changement se lit dans le document AVANT
le changement, et les événements du tampon arrivent APRÈS : l'ancien
texte n'y est plus.

## Ce qui a changé

- **L'ombre de synchronisation** : la liaison garde une copie du
  dernier texte synchronisé par document (`didOpen` la pose, chaque
  `didChange` la met à jour). Le delta se lit entre l'ombre et le
  texte courant : préfixe commun, suffixe commun — la plage de
  l'écart, aux positions du protocole comptées DANS L'OMBRE (les
  coordonnées d'avant le changement, exactement ce que le protocole
  exige), et le texte inséré entre les deux. Une seule plage par
  notification.
- **L'API ne change pas** : `didChange(uri, text)` garde sa signature
  — l'hôte continue d'apporter le texte complet, la liaison n'envoie
  que la plage. Sans ombre (un changement sans ouverture — le montage
  du sample), le texte entier repart : le repli du protocole. Sans
  écart net (les événements amortis s'annulent), rien ne part : le
  serveur tient déjà le document exact.
- **Le serveur de démonstration applique les plages** : un vrai
  serveur remplace la plage reçue — le serveur de démo fait
  désormais pareil (les positions du protocole y retournent au
  décalage, en unités UTF-16 comme les index de `String`).
- Les colonnes restent en unités UTF-16 des deux côtés — celles de
  `String`, celles du protocole : aucun décalage ne s'y glisse.

## Ce qu'on voit (comment rejouer)

    ./gradlew check
    bash scripts/open-harness/run.sh

Sur l'appareil : brancher le LSP (« LSP »), taper une parenthèse
ouvrante puis la fermante — les diagnostics montent à 1 puis
reviennent à 0 : DEUX deltas appliqués bout à bout sur l'ombre. Le
gain se paie surtout sur le hors normes : la parenthèse coûte quelques
octets au lieu de 1,35 Mo.

## Résultats constatés

| Mesure | Valeur |
| --- | --- |
| Tests au dépôt | 120 méthodes de test vertes (128 exécutions, l'éditeur paie deux variantes) — :lsp en compte 8 : les deltas parlent (remplacement, enchaînement sur l'ombre, ajout, suppression multi-lignes), le saut sans écart, le repli sans ouverture |

## Limites assumées (et suite)

- Le diff préfixe/suffixe envoie UNE plage : deux éditions éloignées
  dans la même fenêtre d'amortissement n'en font qu'une (la plage
  couvre l'intervalle) — correct, simplement moins optimal qu'une
  liste de plages.
- L'ombre vit par URI : deux documents distincts tiennent leurs
  ombres ; la liaison n'a pas de `didClose` (le repli plein texte
  couvre l'oubli d'ouverture).
- Le survol reste bloquant à 200 ms dans la popup (le serveur de
  démonstration répond dans le processus) — un serveur réel
  demanderait la voie asynchrone.
- Les suites restantes : le branchement d'un serveur de langage RÉEL
  (`overProcess` y est prêt et testé — le delta le rend enfin
  praticable sur de grands documents), la recherche incrémentale, le
  drag-and-drop de texte, la consolidation.
